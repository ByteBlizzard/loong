# Loong 程序语言设计文档（讨论稿）

**版本**：0.1（讨论汇总稿）
**定位**：一门面向 AI 编程场景、以显式结构为核心、可编译到 JVM 并复用现有生态的通用程序语言
**设计原则名**：榫卯原则

> **Loong 是一门显式结构语言，遵循榫卯原则：构件显式咬合，不依赖胶水与钉子；引用显式自包含，不依赖隐式解析。**

---

## 1. 背景与设计目标

### 1.1 出发点

现有主流语言是为人眼阅读、人手指输入而设计的。AI 编程时代，AI 的认知带宽与错误模式与人类不同：

- AI 擅长局部模式补全，不擅长长程一致性；
- AI 的错误高发于“局部合理、全局漂移”；
- AI 的能力寄生在人类可读代码语料上，因此不能抛弃人类可读性去追求纯机器原生表示。

Loong 的目标不是发明一门“给 AI 看的机器码”，而是在**保持人类可读主干**的前提下，把正确性责任从“AI 的长程一致性”转移到“编译器与工具链的确定性检查”，并让 AI 的操作对象从文本文件变为结构化 AST 节点。

### 1.2 核心设计目标

| 目标 | 含义 |
|---|---|
| **显式大于隐式** | 类型、依赖、引用、副作用、错误路径全部显式，禁止隐式推导与隐式作用 |
| **局部可验证性** | 一段代码的行为应能仅凭局部节点与其显式签名推断，禁止宏、继承、AOP 等远距离作用 |
| **编译快、反馈即时** | 节点级增量编译，结构化诊断，AI 开发循环短 |
| **复用现有生态** | 编译到 JVM 字节码，直接调用 Java/Kotlin 库，不做玩具式新生态 |
| **人类可读与机器可操作统一** | AST 是一等公民，人类可读文本是 AST 的确定性渲染视图 |
| **规则由编译器强制** | 强制注释、强制测试、函数长度限制等纪律，不靠 review 维持，由编译器拒绝违规输入 |

### 1.3 明确的非目标

- 不做纯机器原生表示、抛弃人类可读性的语言；
- 不追求“无语料全新语言 + 纯 AI 生成”的激进路径作为首选；
- 首版不追求跨平台多后端，先做好 JVM；
- 不引入 `async/await` 语法糖，并发靠轻量级线程（JVM 虚拟线程）。

## 2. 语言语法与语义

### 2.1 语法风格基准

大括号、`name: Type` 标注、显式返回类型，接近 Rust / TypeScript / Kotlin 的混合体——这是 AI 训练语料中密度最高、歧义最小的风格。

### 2.2 支持的语法特性

**声明**

| 特性 | 边界 | 理由 |
|---|---|---|
| `module` | 每文件一个模块，文件顶部声明 | 模块边界显式，增量编译单元明确 |
| `depends` | 模块级显式声明依赖的模块全名与版本约束 | 依赖图是一等元数据，不从引用推导 |
| `interface` | 纯方法签名集合，无字段、无默认实现 | 唯一的跨模块契约面 |
| `struct` | 字段名 + 类型显式；无内联方法 | 数据与行为分离 |
| `impl` | 显式 `impl Interface for Struct`；签名必须与 interface 完全匹配 | 名义类型，无隐式满足 |
| `function` | 参数类型、返回类型、可见性全部显式 | 签名即完整契约 |
| `test` | 内联 `test` 块，必须声明 `target: 函数ID` | 测试与被测函数在 AST 中显式关联 |
| `const` | 模块级常量，必须有类型和值；不可变 | 无复杂静态初始化 |

**类型系统**

| 特性 | 边界 | 理由 |
|---|---|---|
| 名义类型 | 类型相等靠名字，不靠结构 | 无 structural typing 隐式匹配 |
| 泛型 | 支持；类型参数必须有显式约束（`where T: Interface`） | 约束显式，编译器可检查 |
| 枚举/和类型 | 支持；`match` 必须穷尽 | 穷尽性由编译器强制 |
| `Option<T>` / `Result<T, E>` | 内建，无 `null` | 空值路径显式 |
| `let` / `var` | 不可变/可变绑定，所有变量声明必须有类型标注 | 禁止类型推断 |
| 函数类型 | 一等值，可作参数/返回值 | 高阶函数靠具名函数值 |

**表达式与控制流**

| 特性 | 边界 | 理由 |
|---|---|---|
| 字面量 | 整数、浮点、字符串、布尔、数组、map | 无隐式转换 |
| 具名参数调用 | 支持 `f(x: 1, y: 2)` | 参数角色显式，减少 AI 错位 |
| 字段访问 / 索引 | 显式语法 | 无属性访问器隐式调用 |
| 二元/一元运算 | 内建操作符，无重载 | 语义唯一 |
| `if` / `else` | 表达式形式，分支类型必须一致 | — |
| `while` | 显式条件 | — |
| `for-in` | 迭代目标必须实现显式 `Iterable` 接口 | 迭代协议显式 |
| `match` | 穷尽性检查；无隐式 fallthrough | — |
| `return` / `break` / `continue` | 无标签 | 控制流局部化 |

**并发**

| 特性 | 边界 | 理由 |
|---|---|---|
| `spawn` | `spawn f(args)` 启动轻量线程，返回 `Handle<T>` | 映射 JVM 虚拟线程 |
| `join` | 显式等待 `Handle` | 无隐式等待 |
| `channel<T>` | 有类型通道，`send`/`recv` 显式 | 通信路径显式 |
| `shared` | 共享可变状态必须显式标注，通过 `Mutex<T>` 访问 | 数据竞争面显式 |
| 无 `async`/`await` | 同步阻塞风格 + 虚拟线程 | 语法层不引入异步传染 |

**错误处理**

| 特性 | 边界 | 理由 |
|---|---|---|
| `Result<T, E>` | 唯一错误传递机制 | 无异常 |
| 显式 `match` / `if-let` | 错误必须被显式处理 | 无隐式传播、无 `?` 操作符 |

### 2.3 语言级强制规则（编译检查）

| 规则 | 检查方式 |
|---|---|
| 强制 doc 注释 | 每个 `function` / `struct` / `interface` 必须有非空 doc 注释节点，否则 `E_MISSING_DOC` |
| 强制单元测试 | 每个 public `function` 必须被至少一个 `test.target` 引用，否则 `E_NO_TEST` |
| 函数长度限制 | `Block` 下语句节点数超过阈值（如 50）报 `E_TOO_LONG` |
| 模块循环依赖禁止 | `depends` 图必须无环 |
| public 必须在 interface 声明 | 跨模块可见成员必须在 `interface` 中有对应签名 |

### 2.4 不支持的语法特性

**继承与多态**：类继承、接口默认方法、抽象类、方法重写、运算符重载、函数重载、隐式接口满足。

**元编程**：宏（文本/语法/过程宏）、装饰器/注解、运行时反射、编译期代码生成、模板元编程。

**隐式机制**：隐式类型转换、类型推断（含局部）、隐式 `this`/`self`、默认参数、可变参数、通配符导入、隐式错误传播（`?`）、隐式全局可变状态、隐式初始化顺序、`null`。

**语法糖**：`async`/`await`、`try`/`catch`/`finally`、尾随闭包、匿名闭包/匿名函数、字符串插值、属性访问器、解构赋值、多返回值、`goto`。

**并发**：`async`/`await`、隐式锁获取、线程局部存储。

### 2.5 两个需要说明的设计决策

1. **具名参数调用是“支持”而非“不支持”**：它让调用点参数角色显式化，直接减少 AI 传错参数位置的高频错误，是“显式大于隐式”的正向应用。
2. **不支持匿名闭包是最激进的取舍**：代价是高阶函数只能传具名函数值，`map`/`filter` 写起来啰嗦；收益是捕获状态完全显式。若后续发现是瓶颈，可退一步支持**带显式捕获列表的闭包字面量**，但不是回到隐式闭包。

**核心逻辑**：凡让“这段代码的行为”无法仅凭局部节点推断的特性，一律不进入语法层。

## 3. 名字解析与模块依赖

### 3.1 模块依赖显式声明

依赖关系是模块级一等声明，独立于任何引用：

```
module foo
depends bar, baz
```

这条声明定义模块 `foo` 的完整依赖闭包，编译器据此构建依赖图、做循环依赖检查、确定增量编译边界。`depends` 与“引用了哪些符号”是两件不同的事。

### 3.2 AST 层不需要 import

import 的本质是“文本层的名字缩写约定”，在 AST 层是冗余的。跨模块引用的正确形态是**全限定名 + 稳定 ID**：

```
Path { name: "bar.Point", resolved_id: <bar 模块中 Point 的节点 ID> }
```

`resolved_id` 由编译器在名字解析阶段填充。AI 工具查询“这个引用指向谁”，直接读 `resolved_id`，不需要解析 import 表、不需要推断作用域规则。**引用是自包含的**。

### 3.3 别名：AST 层不允许，文本视图层由渲染器确定性计算

- **AST 层不允许别名**：别名是间接层，AI 看到 `P` 需要查符号表才知道它是 `bar.Point`，违背引用自包含；别名表是需维护的集中状态，修改会远距离改变语义。
- **文本视图层不需要显式别名语法**：渲染器默认渲染模块路径最后一段（`bar.Point` → `Point`），冲突时自动渲染更多段，映射确定性计算、不存储、不持久化。
- **唯一保留的“命名”机制是导出方的 interface 导出名**：这是封装契约，不是导入方别名。

### 3.4 别名与重构

**全名引用对重构更有利**：移动符号、重命名、拆分模块时，工具按 `resolved_id` 精确匹配，影响范围可计算（数据库一次索引查询）。**别名对重构是净负面**：别名表是额外状态，重构需同时更新引用和别名表，可能不一致；多个别名表协调是分布式一致性问题；改一个名字会扇出成改 N 个引用点。

## 4. AST 设计

### 4.1 设计原则

- **一个节点 = 一个语义决策点**，粒度匹配 AI 的修改粒度。
- **注释和测试是一等节点**，编译器才能强制检查其存在。
- **稳定 ID 是核心机制**：编辑不改变已有节点 ID，删除不复用。AI 的编辑指令是“修改节点 `f3a2`”，而非“改第 47 行”，摆脱行号漂移。

### 4.2 通用节点结构

```
Node {
  id:     NodeId            // 稳定唯一，单调分配，永不复用
  kind:   Kind              // 枚举，决定 fields 和 kids 的解释
  fields: Map<str, Value>   // kind 特定字段
  kids:   [NodeId]          // 有序子节点引用
  parent: NodeId            // 反向引用，便于工具局部重建
}
```

节点存于以 ID 为键的表，`kids` 只是 ID 列表，移动/重排子节点是 O(1) 引用修改。

### 4.3 节点清单（最小完整集）

**声明类**

| kind | fields | kids |
|---|---|---|
| `Module` | name | Import\*, Decl\* |
| `Depends` | module_name, version_constraint | — |
| `Function` | name, visibility, return_type, doc_id | Param\*, Block |
| `Param` | name, type | — |
| `Struct` | name, visibility, doc_id | Field\* |
| `Field` | name, type, doc_id | — |
| `Interface` | name, visibility, doc_id | MethodSig\* |
| `MethodSig` | name, return_type, doc_id | Param\* |
| `Test` | name, target_id, doc_id | Block |
| `DocComment` | text | — |

**语句类**：`Block`、`Let`、`Assign`、`If`、`While`、`Return`、`ExprStmt`。

**表达式类**：`Call`、`Binary`、`Unary`、`Literal`、`Path`（含 `resolved_id`）、`FieldAccess`、`Index`。

`Path.resolved_id` 由编译器在名字解析阶段填充；工具想知道“这个调用指向哪个函数”，查此字段即可。

### 4.4 强制规则如何落到节点上

全部由编译器在 AST 层面检查，AI 无绕过余地：

- **强制注释**：`Function`/`Struct`/`Field` 的 `doc_id` 必须非空，否则 `E_MISSING_DOC`。
- **强制单元测试**：每个公开 `Function` 必须被至少一个 `Test.target_id` 引用，否则 `E_NO_TEST`。
- **函数长度限制**：`Block` 下语句节点数超过阈值即 `E_TOO_LONG`（节点计数，非行数统计）。
- **严格模块化**：跨模块 `Path.resolved_id` 只能指向目标 `Module` 的 `Interface` 下暴露的 `MethodSig`，指向内部 `Function` 是 `E_PRIVATE_ACCESS`。
- **摒弃继承/宏**：节点种类里没有 `Class`、`Macro`、`Expand`，语法上无法表达。

### 4.5 工具 API 与反馈

AI 不写文本，而是调用编辑操作：

```
insert(parent_id, index, node) -> node_id
replace(id, fields?, kids?) -> [affected_ids]
move(id, new_parent_id, index) -> [affected_ids]
delete(id) -> [affected_ids]
get(id) -> Node
find(kind, filter) -> [node_id]
```

每次操作返回受影响节点 ID 集合，编译器据此做**节点级增量重编译**——只重算脏节点所在模块，这是“编译很快”的来源。反馈是结构化诊断：

```
Diagnostic { node_id, severity, code, message, suggested_fix? }
```

### 4.6 文本视图与版本控制

AST 是人类可读文本的派生视图：工具把 AST 渲染成类 Rust 语法的只读文本供人 review；版本控制里存 AST 的规范化序列化（节点按 ID 排序的 JSON），diff 显示节点级增删改，比文本 diff 更精确。

## 5. 运行时与平台策略

### 5.1 主平台：JVM（纯 JVM，不混合）

选择理由：

- **轻量级线程**：JVM 的 Project Loom 虚拟线程，由 JVM 用户态调度，同步阻塞风格直接映射，无需 `async/await`。
- **生态复用**：编译到 JVM 字节码意味着直接调用海量 Java 库。
- **编译速度可控**：JVM 慢的是 Maven/Gradle 而非 javac；自研极速编译器直通字节码、绕开重型构建工具，可获得接近编译器本身速度的反馈循环。
- **历史验证**：Kotlin、Scala、Clojure、Groovy 证明“新语言 + JVM 生态”可行。

### 5.2 为什么不是 Wasm / CLR / 纯原生

- **WebAssembly**：Winch/Singlepass 编译极快，但沙箱隔离使其无法直接链接宿主原生库，生态复用是硬伤；WASM-GC 与线程成熟度不及 JVM。适合作为未来可选的并行快速后端，但不作主平台。
- **CLR**：NativeAOT 构建慢，与快速反馈矛盾；生态互操作广度不如 JVM。
- **纯原生**：Cranelift 可调编译速度，但失去“复用现有平台生态”的杠杆，违背非玩具底线。

### 5.3 平台抽象：核心库与平台库分离

参照 Rust 的 `core`/`alloc`/`std` 分层：

**核心库（平台无关，尽力小）**

- 基础类型与字面量操作：整数、浮点、布尔、字符、不可变 UTF-8 字符串，算术/比较/位运算，显式转换。
- `Option<T>` / `Result<T, E>` 及其组合函数。
- 固定大小集合：固定长度数组、切片、元组（不需要堆分配）。
- 迭代器接口与基础适配器：`Iterator`、`map`、`filter`、`fold`、`take`、`skip`。
- 数学与文本基础：min/max/abs、浮点分类、字符分类与基本 Unicode 属性、字符串 `len`/字节访问/切片。
- 并发原语的**类型与接口定义**：`Mutex<T>`、`Channel<T>`、`Handle<T>` 的签名；实现由平台库提供。
- 编译期支持：`test` 块、`doc` 注释节点的解析与检查属于编译器前端。

**平台特定库（JVM 首版）**

| 能力类别 | 具体内容 | 不属于核心库的原因 |
|---|---|---|
| 堆分配与动态集合 | `Vec<T>`、`Map<K,V>`、`StringBuilder`、`Box<T>` | 需要 GC |
| 控制台与文件 I/O | `print`/`println`、文件读写、路径操作 | 依赖 OS |
| 时间与日期 | 时钟、日期解析/格式化 | 依赖系统时钟与时区数据 |
| 网络 | TCP/UDP socket、HTTP 客户端基础 | 依赖 OS 网络栈 |
| 线程创建与调度 | `spawn` 实现、线程池、`join` 阻塞语义 | 映射 JVM 虚拟线程 |
| 同步原语实现 | `Mutex` 映射到 `java.util.concurrent` | 依赖平台同步机制 |
| FFI | 调用 Java 方法、访问 Java 类 | JVM 互操作 |
| 格式化与解析 | `format`、数字/日期解析、JSON/CSV | 体积大、非必需，适合独立模块 |
| 排序与搜索 | 通用排序 | 依赖分配或迭代器组合 |

**边界强制**：核心库模块不允许 `depends` 任何平台模块，由编译器强制，确保可移植性不靠纪律。未来扩展 WASM/.NET 时，只需为新平台实现对应 `Platform.*` 模块，核心库一行不改。

## 6. JVM 互操作

### 6.1 总原则

互操作是 **API/ABI 问题**：新语言编译产物是 JVM 字节码，Java/Kotlin 也是；在 JVM 看来它们只是不同 `.class` 文件。关键在新语言编译器生成符合 JVM 调用约定的字节码。

### 6.2 Loong 调用 Java/Kotlin

通过**显式的、结构化的外部声明**（声明目标类全名、方法名、参数类型、返回类型），编译器按目标方法性质生成字节码指令：

| Java 目标 | 字节码指令 |
|---|---|
| `static` 方法 | `invokestatic` |
| 实例方法（非接口） | `invokevirtual` |
| 接口方法 | `invokeinterface` |
| 构造器 / 私有方法 | `invokespecial` |

外部声明中的类型必须是 JVM 描述符层面的精确类型。首版只支持静态可确定的外部声明，`invokedynamic` 留给后续动态互操作场景。

### 6.3 Java/Kotlin 调用 Loong

关键是为公开 API 生成**Java 可消费的字节码形态**：

- 公开函数生成 `public` 方法，签名与 `interface` 声明一致。
- 模块级函数与常量归入**由模块名确定的显式宿主类**，类名是 AST 显式属性（不学 Kotlin 的 `FileNameKt` 隐式约定）。
- 没有继承、伴生对象、属性访问器语法糖，公开 API 字节码形态由 `interface` 声明唯一确定，不需要注解修补可见性/静态性。

### 6.4 类型映射与空安全

- **原始类型与装箱**：公开 API 使用原始类型时生成原始类型签名（`I`/`J`/`Z`），避免 Kotlin 式“根据上下文变化”的歧义；`Int` 与 `Int?` 在 AST 中是不同节点，编译器确定性选择原始或装箱。
- **空安全单向收窄**：Loong 接收 Java 引用且声明非空时，编译器在方法入口生成显式非空断言，Java 传 `null` 在边界立即失败；Loong 暴露给 Java 的可空类型在字节码层面是普通 `String`，Java 侧自行判空。不对称是 JVM 现实，主动边界断言更务实。
- **`Result<T, E>`**：编译为普通类（成功值或错误值的联合体），Java 侧显式检查状态取值；不映射为 Java 异常（异常是隐式控制流转移，与显式原则冲突）。

### 6.5 发布物双形态

新语言库发布物包含：**JVM 字节码**（供 Java/Kotlin 消费，只消费字节码）+ **结构化接口 AST**（供 Loong 消费方编译器做类型检查与 `resolved_id` 填充）。互操作不需要桥接层或绑定生成器。

### 6.6 未来对接 .NET / Node.js

**不支持 `async/await` 不构成根本障碍**：

- **.NET**：机制同构，JVM 虚拟线程与 CLR `Task` 可通过现有桥接方案（如 `JCOBridge`）映射；难点是异常传播与取消语义的跨边界对齐。
- **Node.js**：模型异构（单线程事件循环），需边界适配策略——阻塞桥接（独立虚拟线程发起调用并同步等待，跨边界有编组开销）或利用 GraalVM 等多语言宿主。
- 异步适配放在未来对应平台的 `Platform.Interop` 模块，核心库保持不变；真正的成本是**边界适配层的工程复杂度**，而非语法缺失。

## 7. 编译与包管理

### 7.1 编译模型：依赖编译结果，不导入源码整体编译

**编译时只依赖编译结果（字节码），不把依赖库源码导入当前项目整体编译。** 理由：

- 编译速度：依赖库一次编译、多次复用，编译时间不随依赖树线性增长。
- 严格模块化：编译边界与模块边界一致，内部实现变更不触发消费方重编。
- 确定性：构建输入是内容寻址的字节码，配合签名和构建证明。

### 7.2 发布物三层信息

| 层 | 内容 | 谁消费 | 是否参与编译 |
|---|---|---|---|
| 编译产物 | 目标平台字节码（JVM 首版即 class 文件）+ 符号表 | 消费方链接器/运行时 | 是，链接输入 |
| 接口 AST | `interface` 块结构化节点：方法签名、泛型约束、`Result`/`Option` 返回、`proof_require`/`proof_ensure` 合约、文档注释 | 消费方编译器前端 | 是，类型检查与 `resolved_id` 填充 |
| 实现 AST（可选） | 完整模块 AST 快照 | 消费方 AI 工具/IDE，不进入编译图 | 否，只读查询 |

**接口 AST 是编译必需的，实现 AST 是工具可选的。**

### 7.3 编译器如何使用三层

1. 加载依赖的接口 AST，注册符号，建立全名到 `resolved_id` 的映射。
2. 消费方全名引用通过该表解析为依赖模块节点稳定 ID。
3. 基于接口 AST 做类型检查。
4. 形式化验证时，依赖库合约来自接口 AST 的结构化公式（不能只靠字节码注解字符串）。
5. 链接阶段纳入依赖编译产物。

实现 AST 在编译步骤中完全不读取。

### 7.4 依赖解析：MVS 确定性图遍历

采用 **Minimal Version Selection (MVS)**：

- **确定性**：相同 `depends` 声明集合总产生相同构建列表，不需要 lockfile 保证可复现。
- **无求解器**：图遍历选择“满足所有约束的最小版本”，结果可预测、可解释，AI 不需要理解黑箱求解器。
- **高保真**：选“最近的兼容版本”，接近库作者测试时的状态。

**主版本号进入模块路径**（`org.example.http/v2`），不同主版本视为独立模块，可共存于同一构建图。

### 7.5 重用方式：三种场景

- **消费外部已发布模块**：`depends` 声明全名与最小版本，解析器拉取 AST 快照，合并节点表，填充 `resolved_id`。
- **工作区（Monorepo）内部模块**：源码中 `depends` 写工作区协议（如 `depends workspace:org.example.http`），本地开发指向工作区模块，发布时替换为具体全名+版本约束。
- **私有模块与本地覆盖**：项目级配置中允许路径覆盖或注册表覆盖，规则显式、项目级，不影响模块自身 `depends`。

**Monorepo 发布顺序**按依赖图拓扑序，被依赖模块先发布，工具自动级联更新依赖方 manifest 版本约束（`depends` 已显式声明，无需从 import 推导传播关系）。

### 7.6 供应链安全

**发布侧**：

- **构建证明**：SLSA provenance 或等效，记录输入哈希、构建命令、产物摘要并签名。
- **SBOM**：CycloneDX 或 SPDX 格式，声明完整依赖闭包与许可证，与发布物同一身份签名。
- **内容签名**：Sigstore cosign 等对 AST 快照哈希签名。

**消费侧**：

- 解析器验证签名和 SBOM，拒绝未签名或不匹配的发布物。
- AI 生成的依赖声明必须存在于注册表“已验证命名空间”，不存在则解析直接失败（全名引用无别名/通配符可“碰巧”解析到幻觉目标）。
- 可选高安全模式：只允许白名单注册表/命名空间，拒绝发现式拉取。

## 8. 工具形态与最终用户体验

### 8.1 总体架构：语言守护进程（language daemon）

```
┌─────────────────────────────────────────┐
│           loongd (daemon)               │
│  ┌─────────┐ ┌─────────┐ ┌───────────┐  │
│  │ AST 存储 │ │ 编译引擎 │ │ 测试运行器 │  │
│  └─────────┘ └─────────┘ └───────────┘  │
│  ┌─────────┐ ┌─────────┐ ┌───────────┐  │
│  │ 依赖解析 │ │ 版本历史 │ │ 诊断聚合   │  │
│  └─────────┘ └─────────┘ └───────────┘  │
│              ▲ 统一操作 API ▲             │
└──────────────┼──────────────┼───────────┘
               │              │
        ┌──────┴─────┐  ┌─────┴──────┐
        │ Web UI     │  │ MCP Server │
        │ (人类)      │  │ (AI agent) │
        └────────────┘  └────────────┘
```

**状态在 daemon 里，不在文件系统，也不在任何一个前端里。** Web UI 和 MCP 都是瘦客户端，所有变更通过 daemon 的单一操作 API 落到同一份状态。

### 8.2 核心服务层

- **AST 存储**：稳定 ID 节点表，内存热状态，周期性持久化到嵌入式数据库（H2，保持全 JVM 生态）。
- **编译引擎**：节点级增量编译，只重算脏节点所在模块，产出结构化诊断，按节点 ID 索引。
- **测试运行器**：按 `test.target` 关联被测函数，支持增量测试，结果按节点 ID 索引。
- **依赖解析**：MVS 图遍历，拉取并验证 AST 快照（签名、SBOM、构建证明）。
- **版本历史**：整代码快照提交图，不可变快照 + 父提交引用，支持分支、节点级 diff、检出历史版本。
- **诊断聚合**：编译错误、测试失败、依赖冲突、验证失败汇总到可查询诊断池。

### 8.3 MCP 接口（AI agent 操作面）

**读操作**：`get_node`、`find_nodes`、`get_module_interface`、`get_dependencies`、`get_diagnostics`、`get_test_results`、`search_symbol`。

**写操作**：`insert_node`、`replace_node`、`move_node`、`delete_node`；每次写操作自动触发增量编译，诊断随响应返回。

**构建与测试**：`run_tests`、`check`。

**依赖与发布**：`add_dependency`、`remove_dependency`、`publish`。

**版本**：`commit`、`diff`、`checkout`。

**协作**：`request_human_review(node_ids, reason)`，挂起 AI 后续操作直到人类响应。

**边界**：AI 不能直接写文件，只能通过节点操作改 AST；写操作自动触发编译，不能绕过检查；依赖变更走显式 API 且有审计记录。

### 8.4 Web UI（人类观察与控制面）

页面：**代码视图**（AST 渲染文本，悬停显示稳定 ID 和诊断）、**依赖图**（模块有向图，MVS 版本，冲突高亮）、**测试面板**（按被测函数分组）、**诊断池**（聚合列表，按节点跳转）、**版本历史**（提交图可视化，节点级 diff）、**AI 活动流**（实时显示 agent 行为，`request_human_review` 请求在此弹出）、**发布面板**（版本 bump 预览、接口 AST 变化、确认发布）。

核心价值：**让人类监督和干预 AI 开发过程**，不逐行读代码，而是看诊断、测试、依赖变更，在关键节点 review。

### 8.5 人机协作模型

- **共享状态，实时同步**：所有操作串行化到 daemon 操作队列，每次操作后向两个前端广播变更（Web UI 用 WebSocket，MCP 用通知）。
- **双向可见**：AI 改动人类可见，人类改动 AI 可见，不存在状态不一致。
- **审批门显式**：可配置“所有写操作自动执行但 commit 前需人类批准”“修改 interface 节点必须 review”“完全自动，人类事后审计”等规则，是 daemon 配置，不是 agent 自觉。
- **回滚节点级**：检出上一个 commit，或用 diff 定位问题节点单独 revert。
- **并发串行化**：操作队列保证一次只有一个操作执行，人类和 AI 不会同时改同一节点。

### 8.6 一次完整开发循环（示例）

人类在 Web UI 输入需求：“实现一个 HTTP 客户端模块，依赖 `org.example.http/v1 >= 1.2.0`”。

AI 通过 MCP：

1. `add_dependency` → daemon 解析 MVS，拉取接口 AST，更新依赖图，Web UI 实时显示。
2. `get_module_interface` → 拿到 `Client` 签名和合约。
3. `insert_node` 创建函数骨架 → 自动编译返回 `E_MISSING_DOC`。
4. 补 doc 注释，再编译，诊断清除。
5. 实现函数体，每步写操作都返回诊断，直到编译通过。
6. 创建 `Test`，强制测试规则满足。
7. `run_tests` → 通过。
8. `request_human_review` → Web UI 弹出 review 请求，人类批准。
9. `commit` → 版本历史新增提交。

人类只在第 8 步介入一次，其余时间 Web UI 是观察窗口。

### 8.7 CLI：第三个瘦客户端

**双模式**：

- **daemon 客户端模式**（默认）：`loong` 自动发现本地 daemon，命令转发，复用热状态，毫秒级返回。
- **独立模式**（`--standalone`，或 daemon 未运行时自动回退）：CLI 内嵌完整引擎，冷启动执行，完成即退出，适合 CI、脚本、一次性集成。

**承诺**：同一条命令在两种模式下产生相同结果和相同退出码。

**子命令集**（与 MCP 工具对称）：

- 构建与检查：`check`、`build`、`test`
- 依赖：`deps add`、`deps remove`、`deps tree`、`deps verify`
- 节点查询与编辑：`query node`、`query find`、`query symbol`、`edit replace`
- 版本与发布：`commit`、`diff`、`checkout`、`publish`
- 运行：`run`、`exec`
- daemon 管理：`daemon start`、`daemon stop`、`daemon status`、`mcp --stdio`

**输出契约**：默认人类可读文本；`--json` 输出带 `schema_version` 的结构化数据。

**退出码稳定语义**：0 成功、1 编译/类型检查失败、2 测试失败、3 依赖解析或验证失败、4 内部错误。

**可嵌入库形态**：CLI 是薄壳，所有逻辑在 `loong-engine` 库中；集成方可选择进程调用 CLI、链接 `loong-engine` 库、或连接 daemon 的 HTTP/socket API，三者语义一致。

### 8.8 与 MCP 的关系

MCP 给 AI agent（长连接、有状态、双向通知）；CLI 给脚本/CI/其它程序（一次性、无状态、退出码+JSON）。两者覆盖不同集成场景，调用同一套 daemon 操作 API，行为不分叉。

## 9. 形式化验证（**已决移除**：功能未成熟，需要时再引入）

### 9.1 定位

形式化验证是**按包启用的可选能力**，不是语言本身的形式语义核心。它把正确性责任从“AI 的长程一致性”转移到“数学证明器”。

### 9.2 具体内容

- 用 `proof_require` / `proof_ensure` 写合约，`.mbtp` 风格文件定义谓词，循环不变量写在 `where` 块中。
- `loong prove` 将程序翻译为 Why3，再交给 Z3/cvc5/alt-ergo 求解。
- 跨模块合约来自依赖库接口 AST 中的结构化公式，验证器直接消费，不需重新解析文本。

### 9.3 现实约束

- 形式化验证成本高，应**限定核心子集**：安全/关键模块只使用已被形式化的构造。
- 循环不变量与证明编写门槛高，当前工作流仍是“AI 写代码 + 人类或 AI 反复试错写证明”，离“AI 自动生成可证明代码”的闭环有距离。
- 类型系统可视为公理语义的轻量级可自动化片段；形式化验证是其加强版。

## 10. 与现有语言的对比定位

### 10.1 为什么不是 MoonBit

MoonBit 是真实可用的“AI 辅助工作流优化”新语言（`declare` 关键字、按包启用的形式化验证），但在两点上不满足 Loong 框架：

- **语言本身没有形式化语义核心**：验证是叠加的可选层，核心包仍只有类型系统兜底。
- **全新语言的无语料困境未被真正解决**：靠工具链补偿语料缺失，是绕过而非解决训练分布问题。

### 10.2 为什么不是 Rust 作为最终形态

Rust 是成熟通用语言中相对最符合框架的选择（类型系统作为编译期审查层、结构化错误、丰富验证工具生态），但：

- **编译速度慢**：深度静态分析绑在每次最普通的构建上，与 AI 高频迭代循环冲突。
- **严格检查频率与验证需求不匹配**：并发竞态等检查无需每次编译都全量付出。
- **Rust 消除的是最难审查的一类 bug**，不消除业务逻辑错误；Loong 通过“先快循环、后收敛”的分阶段策略缓解这一矛盾。

### 10.3 为什么不是 JVM 企业级 Java

JVM 运行时/字节码层面相对友好（字节码作为跨语言形式化验证的稳定锚点），但典型企业级 Java 的依赖注入、AOP、注解处理器系统性地破坏局部可验证性——这是 AI 在 Java 基准上得分惨淡的根本原因，而非 JVM 的过错。

## 11. 待决事项

1. **模块全名规范**：采用反向域名（`org.example.http`）还是 `loong.` 前缀？将直接影响 daemon、CLI、包注册表三者接口一致性。
2. **`.loongast` AST 快照的规范化序列化格式**：节点排序、哈希算法、签名覆盖范围需定稿。
3. **匿名闭包的最终取舍**：是否支持带显式捕获列表的闭包字面量，需等实际使用反馈。
4. **形式化验证的集成深度**：已决——形式化验证整体移除（功能未成熟），`proof_*` 语法不再计划。
5. **数据库选型**：已决（2026-10-29）——采用 **H2 2.x**（JVM 纯 Java 嵌入式数据库）。理由：daemon 为单写者进程，无跨进程并发访问数据库的场景，H2 相对 SQLite 的并发短板不构成约束；工具链保持全 JVM 依赖，构建、分发与 native-image 更简单。快照与版本历史的可移植事实源是 `.loongast` 规范序列化文本，数据库仅为内部持久化实现，隔离在存储接口（`StoragePort`）之后，可替换。
6. **CLI 短别名策略**：是否官方提供 `lg` 等短别名，还是让用户自行 alias。
7. **跨平台扩展路线**：WASM 后端作为“快速内循环草稿纸”是否值得投入，或等 JVM 生态成熟后再评估。
